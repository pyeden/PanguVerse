# 原子工作台：AI 驱动 + 人工协作 · 设计文档（待审查，未动代码）

> 触发：使用者反馈「界面只像 API 测试工具，没体现 PanguVerse 的定位」。
> 本文只做设计与差距分析，**不含任何代码改动**。审查通过后再拆实现契约。

---

## 0. 一句话结论

现在的 Web 是「**测试执行器**」的外壳：项目/套件/运行三级结构解决的是"跑什么、跑得怎么样"，
但 PanguVerse 的定位是「**把任意业务拆成原子、再由 AI 组合**」。缺的是中间那条主链：

```
自然语言意图 → AI 提议的原子组合（可视化） → 人工审阅/改步骤/调参 → 单步调试 → 确认发布 → 运行与回归
```

没有这条链，平台就只是"另一个 API 测试面板"。

## 1. 现状审查（基于代码，不是印象）

### 1.1 后端已有的能力（被界面埋掉了）

| 能力 | 代码位置 | 现状 |
| --- | --- | --- |
| 原子契约（端口/副作用/能力/恢复策略） | `core/atom.py`、`core/contract.py` | 完整，含 `input_ports`/`output_ports`/`effects` |
| 分子 = 步骤序列，`.seal()` 后成为新原子 | `core/molecule.py` | 完整，`Step` 有 `with/capture/when/foreach/retry` |
| 组合与封存 | `axe/axe.py::compose/seal_molecule` | 完整，但**只能代码调用**，无 HTTP 入口 |
| 规划（LLM / 规则） | `axe/planner.py`、`axe/llm.py` | 完整，产出 `TestPlan` |
| 计划校验 | `axe/plan.py::validate`、`core/validation.py` | 完整，但只在执行前跑一次，不对外 |
| 执行器（重试/自愈/变量传递） | `engine/executor.py` | 完整，**只能整体执行**，无单步 |
| 领域包/原子注册表 | `core/registry.py`、`packs/*` | 完整，UI 只能"看" |

### 1.2 结构性的三个断点

1. **计划是"线性步骤列表"，不是可编辑图**：`TestPlan.cases[i].steps[]`，变量靠 `${...}` 字符串引用隐式传递。
   没有显式的「变量 → 节点」依赖边，所以**画不出组合关系**，也没法做"改一步、只重跑下游"。
2. **规划结果是一次性的**：`plan()` 产出后直接 `run()`；中间没有草稿态、没有版本、没有人工修改的落点。
   用户唯一能改的是 `--env` 和场景 YAML 文本。
3. **原子组合能力只在 SDK 里**：`compose()`/`seal()` 无 HTTP API，界面无法"把原子拖成流程"或"把流程存成新原子"。

### 1.3 界面上缺的具体东西（逐条对应你的反馈）

| 你的反馈 | 缺的界面/接口 |
| --- | --- |
| 只能做 API 自动化测试 | 缺「按领域包浏览能力 + 从任意原子起编」的入口；现在原子库只是只读表格 |
| 自然语言驱动原子组合没有可视化 | 缺「意图输入 → AI 草案 → 图/时间线」的链路；`/api/runs` 只有 `mode=intent` 一步到位 |
| 组合后修改调试原子步骤没有 | 缺节点级编辑、单步执行、输入输出查看、局部重跑 |
| 修改调试后的任务确认保存没有 | 缺草稿/审阅/发布三态、版本 diff、封存为新原子 |
| 没体现 AI+人工协作 | 缺 provenance（哪个节点是 AI 提的、哪个是人改的）、缺"锁定/重规划"、缺审批记录 |

## 2. 产品模型（术语先对齐）

| 概念 | 定义 | 与现有代码的关系 |
| --- | --- | --- |
| **Atom 原子** | 固定签名的可调用执行体 | 已存在 |
| **Step/Node 节点** | 一次原子调用（含参数绑定） | `Step` 已存在，缺"端口绑定"语义 |
| **Workflow 流程** | 节点 + 依赖边 + 变量图 | 新增（比 Molecule 多"图"与"元数据"） |
| **Draft 草案** | 未发布的可编辑流程，含 AI 提议与人工修改 | 新增 |
| **Revision 版本** | 草案的每次保存快照 | 新增 |
| **Publish 发布** | 草案封存为原子（可复用）或固化为可运行流程 | 复用 `seal_molecule` |
| **Run 运行** | 流程的一次执行（含单步调试会话） | 扩展 `RunResult` |

## 3. 核心协作模型：AI 提议、人工裁决

### 3.1 三态与流转

```
 意图 ──(AI 规划)──► 草案 Draft ──(人工编辑/锁定)──► 审阅 Review ──(确认)──► 发布 Publish
                        ▲   │                                              │
                        │   └──(单步调试，回写为"已验证"标记)                 ▼
                        └──────────(AI 按反馈重规划未锁定节点)             运行/回归
```

### 3.2 关键规则（这是"协作"的实质，不是口号）

1. **节点级 provenance**：每个节点标记 `origin: ai|human|imported`，并记录 `changed_by/last_modified`。
2. **锁（lock）**：人工改过的节点默认 `locked=true`；AI 重规划**不得**覆盖锁定节点，只能在其前后增补/替换未锁定部分。
3. **差异审阅**：任何一次 AI 重规划产出 `diff`（新增/删除/改参数/改依赖），必须逐条接受或拒绝，不能静默生效。
4. **确认门禁**：未 `approved` 的草案不可运行（可 `dry-run` 调试），避免"AI 随手生成就当真"。
5. **风险提示前置**：带 `mutate` 副作用、破坏性、需要密钥的原子，在草稿阶段就要标出来并要求显式确认。
6. **可追溯**：发布会记录"谁在哪个版本、改了哪些节点、依据哪次调试结果"。

```
全局
├─ 工作台 Workbench（新，一级）
│   ├─ 意图 → 草案（AI 对话式，右侧可展开原子能力面板）
│   ├─ 编排画布（节点图 + 侧栏参数/端口/变量）
│   ├─ 调试面板（单步执行、输入输出、变量快照、局部重跑）

├─ 平台 Platform（已有）
```

**关键**：项目不再是唯一入口。工作台产出的流程，可以**绑定到某个项目**成为套件；

## 5. 页面设计（逐屏）

### 5.1 工作台首页（`#/workbench`）

- 顶部：一个大输入框「你想让机器做什么？」+ 领域包选择（默认"通用"，可选"API测试/文件系统/…"）。
- 右侧：**能力面板**（原子库，按领域包分组，可搜索，显示端口/副作用徽标）。
- 中部：草案卡片列表（最近编辑），每张卡显示：意图摘要、节点数、状态（草稿/审阅/已发布）、最后修改者。
- 底部：示例意图（从当前领域包的模板生成，点击填入）。

### 5.2 草案编排（`#/workbench/{wid}`）

三栏布局：

| 左 | 中 | 右 |
| --- | --- | --- |
| 节点列表（可拖拽排序；AI/人工来源徽标；锁定图标） | 画布（节点卡 + 依赖边；缩放/自动布局；点节点选中） | 选中节点详情：原子、参数、端口绑定、副作用/密钥提示、执行历史（最近一次输入输出） |

- **依赖边**由变量引用推导：`${steps.x.outputs.y}` 或 `capture.token` → 下游 `with.headers.Authorization`。
  推导不出时退化为"顺序边"，并在边上标 `order-only`（诚实标注，不假装有数据依赖）。
- 顶部动作：`AI 重规划`（弹 diff）、`校验`、`调试`、`保存版本`、`审阅`、`发布`。
- 冲突可视化：同一变量被多处写、或读未定义变量 → 节点标红并给修复建议。

### 5.3 调试面板（右侧抽屉或底部面板）

- **单步执行**：从头跑到选中节点，或只跑选中节点（用上次快照的变量）。
- **输入输出查看**：每次执行记录 `inputs/outputs/耗时/错误/重试`；密钥字段打码。
- **变量快照**：当前上下文全部变量（树形，带来源节点）。
- **局部重跑**：改完某节点后，只重跑该节点及其下游（依赖边决定范围）。
- **失败定位**：错误信息 + 断言期望/实际（复用现有报告渲染）。
- 调试不产生正式 run（可选"保存为调试记录"），避免污染历史。

### 5.4 审阅与发布（`#/workbench/{wid}/review`）

- 左侧：变更清单（AI 提议 vs 当前、或版本 A vs B），逐条 `接受/拒绝`。
- 中部：节点图 diff（新增绿、删除红、改参数黄）。
- 右侧：风险清单（破坏性原子、mutate 副作用、密钥、无限循环风险）与校验结果。
- 底部：`提交审阅` → `批准` → `发布`（发布时选择：固化为流程 / 封存为原子进领域包 / 两者）。
- 发布必须填写版本说明；不能空。

### 5.5 项目内「套件」的来源变化

- 套件可以是：① 仓库里的 scenario 文件；② 工作台发布出来的流程（`workflow_id@version`）。
- 项目页新增「从工作台添加流程为套件」，与现有「绑定 scenario 文件」并列。

## 6. 后端处理流程设计

### 6.1 数据模型

```
<workspace>/.panguverse/workbench/<workflow_id>/
├─ workflow.json          # 元信息：名称、意图、领域包、状态、当前版本、锁定集合
├─ revisions/<rev>.json   # 不可变版本快照（图 + 节点 + 绑定 + provenance）
├─ debug/<session>.jsonl  # 调试记录（单步执行输入输出，打码后）
└─ publishes.json         # 发布记录：版本、封存的原子名、时间、操作者
```

`revisions/<rev>.json` 结构：

```json
{
  "rev": 3,
  "created_at": 0, "created_by": "human|ai", "message": "把登录改成复用 token",
  "intent": "登录后下单并校验库存",
  "domain_pack": "api_testing",
  "nodes": [
    {"node_id": "n1", "atom": "http_request", "name": "登录",
     "with": {"method": "POST", "url": "${env.BASE_URL}/login"},
     "capture": {"token": "body.token"},
     "origin": "ai", "locked": false, "verified_at": null}
  ],
  "edges": [
    {"from": "n1", "to": "n2", "kind": "data", "via": "capture.token"},
    {"from": "n2", "to": "n3", "kind": "order"}
  ],
  "env_schema": {"BASE_URL": {"required": true}, "API_PASSWORD": {"secret": true}}
}
```

### 6.2 处理管线

```
意图 ──► Planner(LLM/规则) ──► 计划(线性) ──► Graphifier ──► 图草案(rev0, origin=ai)
                                                      │
                        人工编辑(节点/参数/锁定/重排) ──┤──► 新 revision
                                                      │
                                              Validator(静态)
                                                      │
                                              Debugger(单步/局部重跑)
                                                      │
                                              Reviewer(diff/风险)
                                                      │
                                              Publisher(seal/固化)
                                                      │
                                              Run(项目套件/批次)
```

各环节职责：

| 环节 | 输入 → 输出 | 要点 |
| --- | --- | --- |
| **Planner** | 意图 + 领域包 + 能力清单 → `TestPlan` | 复用现有；新增"只规划未锁定区域"的模式 |
| **Graphifier** | 线性 steps → 节点图 | 扫 `${var}`/`capture` 推导数据边；推导不出退化顺序边并标注 |
| **Validator** | 图 → 错误/警告列表 | 原子存在、必填端口、未定义变量、环检测、副作用/密钥/破坏性提示 |
| **Debugger** | 图 + 起点/终点 → 执行轨迹 | 单节点执行、快照复用、下游重跑、结果不落正式 run |
| **Reviewer** | rev A/B → diff + 风险 | 逐节点对比；锁定集合差异；AI 提议必须逐条裁决 |
| **Publisher** | 图 + 版本说明 → 流程/原子 | 复用 `seal_molecule`；写 publishes.json；生成可绑定套件 |

### 6.3 关键接口（草案）

```
POST /api/workbench/drafts            {intent, domain_pack}        → {workflow_id, rev, graph}
GET  /api/workbench/drafts            ?status=&domain_pack=        → 列表
GET  /api/workbench/{wid}             ?rev=                        → 图 + 元信息
POST /api/workbench/{wid}/replan      {instruction, scope:"unlocked"} → {diff, rev}
POST /api/workbench/{wid}/revisions   {graph, message}             → {rev}
PATCH /api/workbench/{wid}/nodes/{nid} {with?, capture?, locked?, atom?} → {graph, warnings}
POST /api/workbench/{wid}/validate    {}                           → {errors, warnings}
POST /api/workbench/{wid}/debug/step  {node_id, mode:"from_start"|"only"|"downstream", use_snapshot?}
                                      → {trace:[{node_id,inputs,outputs,status,duration_ms,error}]}
POST /api/workbench/{wid}/review      {base_rev, rev}              → {diff, risks}
POST /api/workbench/{wid}/publish     {rev, message, as_atom?, as_workflow?} → {atom_name?, workflow_ref}
```

所有接口需登录；所有出参对 secret 字段打码；图规模上限（如 500 节点）防滥用。

### 6.4 与现有代码的接缝

- **不改** `core/atom.py`、`engine/executor.py` 的语义；新增 `web/workbench.py` + `web/graph.py` 作为**适配层**。
- 单步执行复用 `Executor` 的原子调用，但用独立 `RunContext` 快照，不写正式 run 目录。
- 发布复用 `seal_molecule`，产物进"用户领域包"（`<workspace>/.panguverse/packs/`），不改内置包。
- 图的持久化与现有 scenario 文件**互不影响**；套件可指向 `workflow_id@rev`。

## 7. 分阶段落地

### P0（先把主链打通，可验收）

1. 工作台首页 + 意图创建草案（复用现有 planner）。
2. Graphifier：线性 → 图（数据边推导 + 顺序边兜底），画布可视。
3. 节点编辑（参数/重命名/锁定/增删/排序）+ 静态校验。
4. 单步调试（只跑节点 / 从头跑到节点）+ 变量快照查看。
5. 版本保存 + diff 审阅 + 发布为流程；绑定到项目成为套件。
6. provenance 与锁定规则生效（AI 重规划不动锁定节点）。

### P1

- 局部重跑（下游依赖范围）、调试记录持久化、风险清单强制确认、发布为原子（seal 进用户包）。
- 领域包切换（同一工作台，换个包就是另一类业务）。

### P2

- 版本对比可视化、多人协同审阅、AI 解释节点（为什么这样拆）、从失败运行反推流程。

### 明确不做

- 图灵完备的编程画布（不做循环体/子图嵌套的可视化编辑，先用原子 + 顺序 + foreach 表达）。
- 在线编辑 Python 原子源码（原子由代码仓库提供）。
- 多用户实时协同（CRDT/OT）。

## 8. 验收标准（审查时请重点看这些是否够）

| # | 项 | 判定 |
| --- | --- | --- |
| W1 | 一句话意图 → 可看图草案 | 5 秒内出图 ≥3 节点；每个节点有原子名、参数摘要、来源徽标 |
| W2 | 图能反映真实依赖 | 有 `capture`/`${var}` 的必有数据边；无法推导的边明确标 `order-only` |
| W3 | 改节点能立刻看到影响 | 改参数/删节点后，校验实时给出受影响下游与未定义变量 |
| W4 | 单步调试可解释 | 每个执行节点返回 inputs/outputs/耗时/错误；密钥打码 |
| W5 | 局部重跑范围正确 | 只重跑选中节点与其下游，范围由依赖边决定，不误跑无关分支 |
| W6 | AI 不越权 | 重规划后锁定节点 100% 未变（逐节点 diff 可证） |
| W7 | 发布有门禁 | 未审阅通过的草案不可发布；发布必须填版本说明 |
| W8 | 可复用 | 发布的流程能绑定成项目套件并运行，结果与调试一致 |
| W9 | 领域中立 | 同一工作台切换领域包后，能力面板与模板随之变化，无需改代码 |
| W10 | 安全 | 全程密钥打码；破坏性原子在发布前必须显式确认 |

## 9. 风险与取舍

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| 图推导不准 | 变量引用是字符串，可能漏边/错边 | 显式标注 `order-only`，不假装有依赖；P1 引入"变量绑定"结构化语法 |
| 调试与正式运行不一致 | 快照变量可能与真实运行不同 | 调试结果标"基于快照"，正式运行另存 |
| 图规模 | 大流程画布会卡 | P0 限 200 节点，超出转列表视图 |
| AI 重规划质量 | 现有模型在计数类任务已暴露弱点 | 重规划只产出 diff，人工逐条裁决；不直接改已发布版本 |
| 与现有 API 测试 IA 重叠 | 项目页已是成熟路径 | 工作台是"造流程"，项目是"跑流程"，两入口明确分工 |

## 10. 需要你拍板的三个问题

1. **工作台是否作为一级入口**（与「项目」并列），还是先挂在项目内（"从意图新建套件"）？我倾向前者，否则平台形象还是测试工具。
2. **P0 的发布形态**：先只支持「发布为流程（绑定套件）」，还是同时支持「封存为原子」？后者更能体现"递归组合"，但工作量与风险更高。
3. **调试是否允许直连真实环境**：默认只允许用项目配置的环境跑单步（安全），还是允许临时填任意 URL（方便但危险）？
